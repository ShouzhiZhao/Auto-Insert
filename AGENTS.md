# Agent Guide

This project implements stereo-guided robotic picking and insertion in Python. User procedures and interface contracts are documented in `README.md`. Follow the workflow below to integrate and deliver a task.

## Execution and recovery contract

Apply these rules to task integrations, SDK adapters, subclasses, tests, and handoffs as well as the template itself. User instructions override template defaults. A correction to an unnecessary blocker applies to equivalent checks throughout the workflow, not just the reported exception.

- **Do not invent prerequisites.** Implement the requested sequence. Do not add fixed scene slots, silhouette/color/area acceptance gates, commissioning flags, iteration caps, search-distance caps, or stricter arrival tolerances just because they seem prudent. A new execution stop must follow an explicit task requirement, the SDK/device contract, or a demonstrated physical operating limit. State its source, units, affected stage, and recovery in the existing development record; this is not an additional user-approval step.
- **Keep diagnostics, convergence, and acceptance separate.** SDK-reported position/orientation residuals remain diagnostic when the SDK treats them that way; use the phase's feedback controller to align. A failed timing or physical acceptance result is an experiment outcome, not automatically a reason to abort the experiment or prevent the next trial. An acceptance-time target does not create a watchdog. Use an execution deadline only when the task or device contract actually calls for one.
- **Recover within the authorized task.** A missing observation pauses dependent motion and requests fresh observations; it does not by itself end the rollout or require human intervention. Use `None` or `pick.perception.ObservationUnavailable` for recoverable visual failures so the implemented motion loops retry with fresh images. Do not convert arbitrary SDK/programming errors to visual failures. Observe after every correction, including the last permitted move if the task explicitly specifies a limit. Re-localize moved objects within the requested working range rather than asking the user to restore a detector's preferred slot. Diagnose persistent nonconvergence and revise the implementation instead of waiting indefinitely or silently loosening accuracy requirements.
- **Distinguish action stops from task stops.** Real SDK faults, unavailable control ownership, and measured physical obstructions can stop motion. Continue diagnosis and independent work, use previously authorized recovery, and resume from fresh state when resolved. Do not suppress hardware faults, replay stale commands, reset accumulated insertion progress to evade an actual obstruction, or declare success without evidence. Ask for human intervention only for a concrete step that cannot be completed with available tools and existing authorization; explain that step and what was already attempted.
- **Implement the selected sensing and control method.** Inspect the template and SDK before declaring a capability unavailable. If the user chooses motor-torque force estimation or a force-contact-then-press sequence, implement that choice without adding an unrelated sensor, calibration prerequisite, or mandatory visual acceptance gate. Keep force frames/signs and the distinction between estimated force and physical seating explicit. Template thresholds and step sizes are tuning defaults, not universal limits.
- **Select force feedback by measured stability.** Consider three routes: a force/torque sensor; a model-based joint-torque estimate with gravity compensation and a geometric Jacobian; or measured-baseline subtraction. Test the selected route before using it for control, under the actual phase's poses, payload, and motion speeds. Check noise, drift, repeatability, response to contact/release, and whether contact is distinguishable from free motion. A quiet but unresponsive signal is not a successful test. If relatively stable and informative, consider force feedback preferentially for grasp contact or placement/insertion; evaluate the phases separately. If unstable, generally abandon that route and continue with vision or another suitable method. Do not inflate the force threshold to conceal instability, copy an unrelated task's limits, or turn this development choice into a recurring runtime approval gate. Measured baseline acquisition belongs to the baseline route; it is not mandatory for the other two routes.
- **Choose robust visual features and hardware-appropriate SOTA models.** Prefer repeatable, physically meaningful features that remain identifiable across both views, target relocation, lighting, reflections, viewpoint changes, and gripper/object occlusion. Use visible rigidly related references when the contact point becomes hidden; do not depend on a taught slot, an unstable mask centroid, or a view-dependent silhouette alone. Inspect available local/authorized remote GPU, memory, inference support, and transfer latency, then prioritize current state-of-the-art deep models suited to the required detection, segmentation, matching, or keypoint task. Do not default to a familiar older or CPU-only model without considering the available hardware. Compare viable candidates on representative task images and actual end-to-end latency; prefer demonstrated feature robustness over a SOTA label. Record the selected version, evidence, hardware, and reasons for any lighter/older fallback without creating a new runtime gate.
- **Keep force control independent of vision retries.** During force contact, continue descending and polling force while background vision retries or waits for inference. Missing vision retains the last XY/yaw target; it does not gate Z motion. Apply each new visual result once. Stop on the selected force criterion without waiting for vision, and discard late results when leaving the phase. SDK target replacement must continue an active motion rather than stop/restart at each update.
- **Review behavior, not only exceptions.** Before delivery, inspect new `raise`, early-return, retry/count/distance/time limits, and completion predicates across the changed execution path. Remove unsupported blockers. Test continued execution through the reported recoverable case and preservation of real fault reporting; a test that merely confirms an invented threshold rejects does not justify that threshold. Keep this review in the normal implementation workflow, not a new approval system.
- **Carry decisions forward.** Handoffs record the current user requirements, standing authorizations, removed restrictions and why, genuine unresolved faults, and the next executable step. Do not instruct the next agent to blindly preserve every existing guard. Reconcile older notes with the latest user decisions and current source. Continue useful work while a physical reset is pending.

## Responsibilities

| Location | Responsibility |
| --- | --- |
| `perception.py` in `pick/` and `place/` | Task detection, stereo correspondence, and observation features |
| `calibration.py` in `pick/` and `place/` | Teaching data, Jacobian fitting, motion correction, and model persistence |
| `motion.py` in `pick/` and `place/` | Device commands, actions, and closed-loop control |
| `main.py` | Device and task assembly, action sequencing, and stage parameters |
| `rollout.py` | Event logging, raw image storage, results, and source snapshots |
| `experiments/` | Agent iteration records, frozen-program trials, and independent outcome evaluation |
| `pick/data/` and `place/data/` | Calibration files and rollout data for each phase |

## Implementation SOP

1. **Define the task.** Identify the tool, object, target, grasp and insertion acceptance criteria, working range, and required accuracy. Document the TCP, base frame, camera arrangement, feature correspondences, and initial poses.
2. **Connect the devices.** Implement the robot and camera contracts in the README. Use mm/rad and the ZYX Euler convention consistently. Identify available sensor, gravity-compensated model, and measured-baseline force routes. Force-based contact requires move commands that update the active target during motion.
3. **Establish observations.** Select robust physical features first, then prioritize current SOTA deep learning models compatible with the available hardware for detection, segmentation, matching, or keypoint estimation. They must provide task position and directed orientation. Validate on representative stereo images with variations in lighting, background, occlusion, target position, and object appearance. For placement targets that become occluded, choose a visible reference feature with a fixed spatial relationship to the desired placement location, such as a feature on the same rigid fixture. Teach and calibrate with that feature and retain its definition during execution. Match the same physical features across both views and inspect how observations change under small x/y/z/yaw movements.
4. **Teach and calibrate.** Record separate grasp-alignment and insertion-entry references. Collect positive and negative perturbations along all four axes and samples across the working range. Use held-out samples to evaluate correction direction and accuracy, then save the raw samples, model, and validation results.
5. **Tune each stage.** Test force-signal stability and contact response before selecting force control for that stage; when relatively stable, consider it preferentially for grasp contact or placement/insertion, otherwise favor another suitable method. Retain this selection evidence with the experiment. Tune positioning and contact through begin, approach, and contact, followed by close/lift and press/release. Evaluate grasping, insertion, and release against the task's physical acceptance criteria.
6. **Run the workflow.** Assemble the complete sequence in `main.run()` and record each execution with `RolloutLog`. For agent development experiments, start an iteration before editing, save the actual prompt and feedback, then freeze the candidate with its response, available traces, and measured costs. Run trials from that snapshot and record physical acceptance separately using independent measurements or human observation. Review stage results, task measurements, and recorded data to refine parameters.
7. **Deliver a reproducible task.** Provide device integration instructions, detector and feature definitions, calibration paths, execution commands, and validation records so another user can reproduce the task.

## Code Style

- Perception must prioritize robust features and current SOTA deep learning models appropriate to the available hardware, following the selection rule above. Do not implement core detection solely with hand-tuned OpenCV thresholds, color masks, edges, contours, or template matching. OpenCV may support image preprocessing, camera geometry, visualization, and postprocessing of model outputs. Keep model inference and supporting code in the perception modules.
- `motion.py` must remain concise, showing stage actions, control iterations, and SDK commands directly. Each action method should make its execution order, parameters, and completion condition clear. Keep complex perception, calibration, and logging logic in their respective modules.
- `perception.py` and `calibration.py` serve as entry points. Additional Python files in the corresponding `pick/` or `place/` directory may handle feature extraction, stereo processing, model fitting, or other focused responsibilities. Compose these modules through direct calls with clear inputs and outputs.
- Organize code by task phase and favor direct function calls with explicit data flow.
- Maintain pick and place implementations separately; reuse simple data types such as poses where useful.
- Use specific names to distinguish observations, errors, targets, and measured states. Include units in names or adjacent comments, such as `speed_mm_s` and `height_mm`.
- Keep tuning values close to their use and expose frequently adjusted options as method parameters. Use conventional indentation, leading-zero decimals, and readable expressions.
- Comments explain coordinate frames, units, inputs, outputs, computation, and SDK semantics. Keep operating instructions in the README.
- Separate motion, perception, and logging responsibilities. Record inputs and outputs at call boundaries while preserving arguments, return values, and exception semantics.
- Document current behavior and practical operating steps. Update examples and verify the affected workflow when interfaces or data formats change.
- Write project documentation, code comments, and docstrings in English.

## Data and Validation

Save calibrations with `save()` under the phase's `data/calibrations/` directory, including the taught reference, raw samples, prior, and fitted parameters. A complete workflow shares one run ID across pick/place `data/rollouts/` directories and stores events, raw camera images, calibration copies, source snapshots, and results.

When adding perception or calibration modules, update the source snapshot coverage in `rollout.py` so each run includes the implementation it used.

Validation records describe the environment, test subject, expected outcome, and observed outcome. Identify kinematic demonstrations, image-processing tests, and hardware experiments separately. Record program completion status and physical task acceptance separately.

Use `experiments/data/` for task criteria, agent/model identity, iteration snapshots and diffs, trial output, and assessment evidence. Keep phase calibration and rollout records under `pick/data/` and `place/data/`, linked by the trial ID. An execution exit code describes program completion; physical success comes from a separate evaluator. Leave unmeasured outcomes and unavailable costs unknown. Keep experiment bookkeeping and evaluation outside `motion.py`.

Develop against the current project source; historical snapshots in data directories support experiment reproduction. After implementation, follow the README's integration, calibration, execution, and data-inspection steps to review the user experience.
